# Karpathy 准则

**调用规则：** 只要任务会产出或改动本仓库代码，必须先读完再动手，并按下文执行。

用于减少常见 LLM 编码失误的行为准则，源自 [Andrej Karpathy 对 LLM 编程陷阱的观察](https://x.com/karpathy/status/2015883857489522876)。

**取舍：** 这些准则偏向谨慎而非速度。对琐碎任务请自行判断。

## 1. 先想后写

**不要臆测。不要掩饰困惑。把取舍摆到台面上。**

动手实现之前：
- 明确写出你的假设。不确定就问。
- 若有多种理解，列出来——不要悄悄选一种。
- 若有更简单做法，说出来。该反驳时就反驳。
- 若有不清楚之处，停下来。点明哪里困惑。去问。

## 2. 简单优先

**能解决问题的最少代码。不做臆测性扩展。**

- 不要超出需求加功能。
- 不要为只用一次的代码抽象。
- 不要加未被要求的「灵活性」或「可配置」。
- 不要为不可能发生的场景写错误处理。
- 若写了 200 行本可 50 行搞定，就重写。

自问：「资深工程师会不会觉得过度复杂？」若是，就简化。

## 3. 精准改动

**只动必须动的。只收拾自己弄乱的。**

编辑既有代码时：
- 不要「顺手优化」相邻代码、注释或格式。
- 不要重构没坏的东西。
- 对齐现有风格，即便你自己会换一种写法。
- 若发现无关的死代码，提出来——不要擅自删。

当你的改动产生「孤儿」时：
- 删掉**因你的改动**而不再使用的 import/变量/函数。
- 不要删原本就存在的死代码，除非被要求。

检验标准：每一行改动都应能直接追溯到用户的请求。

## 4. 目标驱动执行

**定义成功标准。循环直到验证通过。**

把任务变成可验证的目标：
- 「加校验」→「为非法输入写测试，再让测试通过」
- 「修 bug」→「写能复现的测试，再让测试通过」
- 「重构 X」→「重构前后测试都通过」

对多步骤任务，先写简短计划：
```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

成功标准越清晰，越能独立迭代。标准含糊（例如「能跑就行」）就会不断需要澄清。
